# Review: BOOLEAN, relations, and control flow

Reviewed against the uncommitted tree on top of commit `4010aeb` ("lexer, parser,
sema, and integer codegen"), implementing the plan in
[../plans/2026-08-02-003-boolean-relations-and-control-flow.md](../plans/2026-08-02-003-boolean-relations-and-control-flow.md).

## Verdict

The slice is correct and complete against its plan. All corpus and error tests
pass, `cargo clippy` is clean, and the two behaviors the plan singled out as
load-bearing — short-circuit evaluation guarding a division, and WHILE/ELSIF
returning to the first guard after any body — are both verified below. One
deliberate deviation from the plan turned out to be an improvement, but it left
behind about seventy lines of dead code in `eval_const`; that is the only
finding of substance.

## Verified behavior

**Short-circuit guards the division.** `build/ShortCircuit.ssa` (generated by
`cargo run -- tests/corpus/ShortCircuit.Mod`) shows the `&` lowering: the left
operand `y # 0` is computed, then `jnz %.t2, @.logic.rhs3, @.logic.short4`, and
the `div` instruction appears only inside `@.logic.rhs3`. The `OR` case is
symmetric. The result temp `%.t0` is assigned in both arms and read after the
join — QBE accepts the non-SSA input as the plan predicted. The binary prints
`12` (guard suppressed the first branch, OR short-circuited the second).

**WHILE with ELSIF re-tests from the top.** `While.Mod` runs the Report's
gcd-by-subtraction on 48 and 18 and prints `6`. In `while_statement`, every
guard body ends with `jmp` back to the single `@.while.test` label, so after an
ELSIF body the first guard is re-evaluated, per Report 9.6.

**Edge cases compiled and run by hand.** The following module exercises empty
THEN and ELSE bodies, assigning a relation result to a BOOLEAN variable,
`&`-binds-tighter-than-`OR` precedence, a WHILE whose body never runs, and a
negated compound UNTIL condition:

```oberon
MODULE Edge;
  IMPORT Out;
  VAR b: BOOLEAN; x: INTEGER;
BEGIN
  IF TRUE THEN END;
  IF FALSE THEN ELSE END;
  x := 5;
  b := x < 3;
  IF b OR (x = 5) & ~b THEN Out.Int(1, 0) ELSE Out.Int(0, 0) END;
  WHILE FALSE DO Out.Int(9, 0) END;
  REPEAT x := x - 1 UNTIL ~(x > 0);
  Out.Int(x, 0);
  Out.Ln
END Edge.
```

It compiles and prints `10` (the `1` from the IF, then `0` from the counted-down
`x`), which is the correct answer.

**Constant folding short-circuits.** `BoolOps.Mod` declares
`Folded = (FALSE & (1 DIV 0 = 0)) OR TRUE`; the fold accepts it without a
division-by-zero diagnostic because `eval_const` never evaluates the right
operand of a decided `&`. The whole expression is still type-checked first, so
an unreachable but ill-typed operand is rejected — see the next section.

## Findings

### Dead type-error arms in eval_const (the one real finding)

The plan said type errors inside constant expressions would be diagnosed by
`eval_const`. The implementation does something better: in `analyze`, every
constant's expression goes through `check_expr` first, and folding is skipped
if that fails. The comment at the call site gives the right reason — folding
short-circuits, but an operand that folding never reaches must still be
well-typed. This is the correct reading of static typing, and the plan's
version would have silently accepted `CONST F = FALSE & (1 & 2)`.

The consequence, though, is that every type-error path inside `eval_const` and
`eval_const_binary` is now unreachable: the `&`/`OR` operand-mismatch arms, the
unary `-`/`~` mismatch arms, the non-Integer arms of the arithmetic and
ordering cases, and the same-type check under `=`/`#`. `eval_const` is called
from exactly one place outside itself, and that call is guarded by a successful
`check_expr`. Per the project's error rules, a broken internal invariant should
crash loudly rather than return a polite diagnostic — these arms should be
`unreachable!()`, which deletes roughly seventy lines. That would also remove
the only callers passing asymmetric arguments to `binary_type_error`, after
which `check_binary_types` and `binary_type_error` can take a single `expected`
type instead of `expected_lhs`/`expected_rhs` (every surviving caller passes
the same type twice).

What genuinely remains reachable in `eval_const` and should keep its
diagnostic: overflow, constant DIV or MOD by zero, and "'x' is not a constant".
The last one is arguably unreachable today too — variables are declared after
constants, so a name in a constant expression cannot resolve to one — but it
will become reachable as declaration forms grow, and it is cheap to keep.

This cleanup was applied in the same commit that lands this review, so the code
as committed no longer shows the dead arms described above.

### Failed constant declarations cascade (minor, accepted)

When a constant's expression fails to type-check, the constant is never
declared, so each later use adds an "undeclared identifier" error. Confirmed
with:

```oberon
MODULE Cascade;
  CONST A = 1 & 2;
  VAR x: INTEGER;
BEGIN
  x := A
END Cascade.
```

which reports the `&` error and then `undeclared identifier 'A'` — two errors
for one mistake. The plan's poisoning rule ("already diagnosed" stays silent)
is applied within expressions but not across declarations. Fixing it would mean
a poisoned-symbol sentinel in the scope, which is more machinery than the
problem deserves this early; the follow-on error at least points at real code.
Noted so the decision is on record, not as a request to change it.

### Plan deviations, all benign

- Labels are `@.<kind><N>` with one global counter (`@.if.end0`,
  `@.logic.rhs3`) rather than the plan's sketched `@if3.then`. Same collision
  argument (leading dot cannot appear in an Oberon identifier), and the kind
  names make the generated IL easy to read.
- Type errors in constant expressions moved from `eval_const` to a `check_expr`
  pre-pass, as discussed above.
- The parser's message for the remaining unsupported statements was tightened
  from "structured statements" to "FOR and CASE statements", which is simply
  more accurate now.

### Not covered by the corpus, verified only by hand

The corpus has no module that assigns a relation result to a BOOLEAN variable
(`b := x < 3`) or uses an empty THEN/ELSE body. Both work — the Edge module
above proves it — but only this review ran them. Worth folding into
`BoolOps.Mod` or a small `Empty.Mod` when convenient; not blocking.

## What was checked and found sound

- Parser follows the grammar: one optional relation per expression (no
  chaining), `OR` in the add-operator loop, `&` in the mul-operator loop, `~`
  at factor level binding tightest. `IN`/`IS`, `FOR`/`CASE` still produce
  "not yet supported".
- Sema poisons instead of cascading within expressions: `check_expr` returns
  `Option<Type>`, and a `None` operand suppresses the parent's diagnostic.
- Equality accepts both types when they match; ordering is INTEGER-only.
  `OrderOnBool` and `AndOnInt` pin the exact messages.
- `Out.Int(TRUE, 0)` is caught by the new per-parameter type list on
  `Symbol::Proc` (`BadArgType` pins it).
- `~x` lowers to `ceqw x, 0`, which is sound because every BOOLEAN value in
  generated code is a normalized 0 or 1: literals emit `1`/`0`, comparisons
  produce 0/1, and the logical join copies one of those.
- `REPEAT` lowers to `jnz cond, @end, @body` — exit on true, correct for UNTIL.
